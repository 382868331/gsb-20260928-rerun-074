# 离线实验资源调度系统（第一版）

纯 Python、零第三方依赖的模拟系统：管理虚拟计算节点、实验需求与运行记录，
在内存与并发双重限制下完成作业放置。项目不连接真实集群，全部行为由
tick 驱动的确定性模拟器复现。

## 运行

```bash
python demo.py          # 场景演示（碎片 / 防饿死 / 节点不可用 / 存盘接续）
python -m pytest tests/ # 8 个测试
```

## 模块

- `scheduler/models.py`：`Node`（内存容量、并发槽、可用标志）、`Job`（实验身份 id 不变）、`RunRecord`（开始即创建、释放即封口）。
- `scheduler/policy.py`：队列策略。
  - `FIFOQueuePolicy`：先到先服务（对照基线）。
  - `FairAgingPolicy`：默认公平策略（见下）。
  策略只决定排队顺序与预留，不改变实验 id。
- `scheduler/scheduler.py`：放置核心与 JSON 快照。
- `scheduler/simulator.py`：事件队列（提交/取消/节点上下线）、时钟推进、存盘/恢复、可行性计划预览。

## 明确的公平策略（大任务不饿死）

`FairAgingPolicy(reserve_threshold=W, aging_factor=α)`：

1. **老化加权**：排队任务动态分 = `priority + 已等待 tick 数 × α`，等待越久排序越靠前。
2. **防饥饿预留**：等待达到 `W` 个 tick 的任务进入预留队列（`RESERVED`），
   按“先进入预留先服务”选定目标节点；该节点释放出的资源被**冻结**，
   只供预留任务使用，新到小任务不能占用。
3. **保守回填**：未预留的小任务仍可使用其它节点和空闲碎片，但不能使用任何预留目标节点。

因此在最恶劣的“持续小任务流 + 长期任务钉住一个槽”场景下，
大任务在进入预留后只需等待目标节点上的在跑任务陆续结束即可启动，
等待上界 = 提交时刻 + `W` + 目标节点在跑任务的剩余时长，**不会无限期饥饿**。
对照测试 `test_fifo_without_reservation_starves_big_job` 证明没有预留冻结时大任务确实会饿死。

## 资源与生命周期规则

- **任务开始才占资源**：`RunRecord` 只在 `_start()` 成功放置时创建；排队/预留不占资源。
- **取消和失败只释放一次**：正常完成、取消、节点故障杀任务都走唯一入口 `_release()`，
  靠“未封口运行记录 + `release_count`”保证幂等；未开始的任务取消不产生任何释放。
- **节点临时不可用**：cordon（默认，在跑任务继续、拒绝新放置）或故障杀任务（`kill_running=True`）；
  恢复后自动继续。预留目标节点不可用时，预留会改挂到其它能容纳的节点。
- **不能安排不存在的容量**：放置前逐节点校验 `已用内存 + 需求 ≤ 容量` 与 `在跑数 + 1 ≤ max_running`；
  需求超过所有节点物理上限的作业提交即 `REJECTED`；放置采用最佳匹配（剩余内存最少优先）以降低碎片。

## 状态保存与接续

`Simulator.save(path)` 保存时钟、节点、作业、全部运行记录、预留队列、未来事件；
`Simulator.load(path)` 恢复后继续 `run_until(...)`，结果与一次性跑完逐作业一致
（见 `test_save_and_resume_matches_continuation`）。队列策略也在快照中，
恢复后可换策略，实验身份（id、priority 等）保持不变。
